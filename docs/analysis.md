## 4. 確定仕様（データと指示書から確定できたもの）

### 4.1 エリア判定の優先順位

指示書 §6・§7 の要求と、データ構造が完全に一致することを確認しました。

1. **駅名の一致**（最優先）
2. **市区町村・区の一致**
3. シートの「それ以外」区分

データ上の裏付け:

| 入力 | 該当 | 根拠 |
| --- | --- | --- |
| 横浜駅 | ① | 東京シート ① の JR 列に「横浜」 |
| 横浜市 | ③ | 東京シート ③ の市区町村列に「横浜市」 |
| 武蔵小杉駅 | ② | 東京シート ② の駅列に「武蔵小杉」 |
| 川崎市 | ③ | 東京シート ③ の市区町村列に「川崎市」 |
| 川崎駅 | ② | 東京シート ② の駅列に「川崎」 |

指示書の 4 例がすべてデータと整合します。**市区町村を先に見ると全部外れる**構造です。

さらに市区町村どうしの照合では **「区」を「市」より先に判定** します。
大阪シートでは ② に `大阪市`、③ に `淀川区`・`東淀川区`・`都島区`・`東成区` があり、
これらはすべて大阪市の行政区です。市を先に見ると ③ の 4 件が永久に到達不能なデータになるため、
「より狭い行政単位を優先する」以外にデータが成立しません。（→ ASSUMPTION-3 として明記）

### 4.2 判定閾値は「エリア × 築年数」ごとに異なる

指示書 §11 は 3.19% 以下 = 割高 / 3.20〜3.39% = 相場通り / 3.40% 以上 = 割安 を「現時点で確認されている
基本基準」としています。データを確認したところ、これは **東京シート ①エリア・築 6〜9 年のセル
`3.20%-3.39%` そのもの** でした。

つまり閾値は全エリア共通の固定値ではなく、**セルのレンジ `[low, high]` から次の一般規則で導かれます。**

```
収益率 <  low            → 割高
low ≤ 収益率 ≤ high      → 相場通り
収益率 >  high           → 割安
```

`[low, high] = [3.20, 3.39]` を代入すると §11 の記述と完全に一致します（3.19→割高、3.20→相場通り、
3.39→相場通り、3.40→割安）。閾値をハードコードせず、この規則をデータに適用します。
§37 で必ずテストするよう指定された 4 つの境界値も、この規則の検証としてそのまま使えます。

### 4.3 相場価格帯

```
月間実質収入 = 月額賃料 − 管理費 − 修繕積立金
年間実質収入 = 月間実質収入 × 12
収益率       = 年間実質収入 ÷ 物件価格 × 100

相場価格（下限） = 年間実質収入 ÷ high   ← 収益率が高いほど価格は安い
相場価格（上限） = 年間実質収入 ÷ low
```

収益率と価格の逆関係が正しく反映されます。また

```
収益率 > high  ⇔  物件価格 < 相場価格下限   （割安）
収益率 < low   ⇔  物件価格 > 相場価格上限   （割高）
```

が数学的に恒等なので、**判定と価格帯は必ず矛盾しません**（判定は丸め前の厳密値で行います）。

### 4.4 駅徒歩分数はデータに条件が存在しない

全 5 シートを走査しましたが、「徒歩」「分」「5分以内」等の区分は **一切ありません**。
指示書 §9 は「データとして存在する場合、データの定義を確認して実装する／データに存在しない条件を
勝手に追加しない」としているため、**駅徒歩分数は入力・保存はするが診断計算には使用しません**。
この点は結果画面には出さず、要件書とマイページの注記に明記します（→ ASSUMPTION-2）。

## 5. 不明点・問題点

### BLOCKER

**BLOCKER-1: 東京シート ④エリア「築35以上」の収益率が `4.70%-4.49%` で下限＞上限**

隣接する築 30〜34 年は `4.60%-4.79%` であり、`4.70%-4.49%` は 4.70 > 4.49 で範囲として成立しません。
`4.70%-4.89%` の誤記の可能性が高いものの、**推測して修正することは禁止事項**のため補正しません。

- 対応: 当該セルを `valid: false` として取り込み、この条件（関東 4 都県／④エリア／築 35 年以上）の
  診断要求に対しては計算を行わず、`DATA_UNAVAILABLE` として「この条件は現在データ準備中です」という
  案内を返します。無料診断回数も消費しません。
- 管理画面のデータ検証ページに BLOCKER として常時表示します。
- **クライアント確認事項:** 正しい値をご指定ください。

**BLOCKER-2: 有料診断の価格と Stripe の商品／価格 ID が未確定**

- 対応: 金額・通貨・課金方式（都度課金 / サブスク）をすべて環境変数化し、
  `STRIPE_PRICE_ID` 未設定時は有料導線を「準備中」として安全に無効化します。コード変更なしで確定値を反映できます。

### ASSUMPTION

**ASSUMPTION-1: 入力項目に「所在地（都道府県・市区町村）」を追加**

指示書 §3 の 7 項目には所在地がありませんが、§6 が要求する「駅名 → 市区町村」の 2 段階照合は
市区町村の情報がなければ成立しません。加えて W-3・W-4 のとおり、駅名・区名はシート間で重複するため
都道府県が分からないと参照シートを特定できません（例:「赤坂」は東京①と福岡①の両方に存在）。

- 対応: **診断の 7 項目はそのまま維持**したうえで、その前段に「物件の所在地」ステップ
  （都道府県セレクト＋市区町村入力）を置きます。指示書 §3 は「基本的に以下の 7 項目を扱う」という
  表現であり、7 項目の変更・削除はしていません。
- **クライアント確認事項:** この追加で問題ないかご確認ください。

**ASSUMPTION-2: 駅徒歩分数は収集・保存するが診断計算には使わない**（§4.4 の根拠による）

**ASSUMPTION-3: 市区町村の照合は「区 → 市」の順**（§4.1 の根拠による）

**ASSUMPTION-4: 相場価格の丸めは「万円単位・四捨五入」に統一**

§10 が「勝手に決めず、ユーザーにとって自然な万円単位等になるよう統一する」としているため、
下限・上限・差額のすべてを 1 万円単位で四捨五入する単一規則にしました。判定自体は丸め前の
厳密値で行うため、丸めが判定を変えることはありません。

| ヘッダー | 上部に細い告知バー → ロゴ＋電話番号＋CTA ボタン 3 種 → グローバルナビの 3 段 | MVP は 2 段に簡素化（告知バー無し、ロゴ＋ナビ＋CTA 1 つ） |
| ページ内ナビ | 見出しへのアンカーリンクを丸印つきで横一列に追従表示 | LP に同型のアンカーナビを採用（スマホは横スクロールではなく省略） |
| 見出し | 中央揃え、太字、前後に大きな余白（80〜120px 相当） | セクション余白 `96px`(PC) / `56px`(SP) |
| カード | 角丸 12〜16px、薄いボーダー＋弱いシャドウ、アイコン＋見出し＋本文＋ボタン | 同型の `Card` コンポーネントを 1 つ定義して再利用 |
| ボタン | 塗り（主）／白地＋枠線（副）の 2 種。角丸大きめ、アイコン付き | 同じ 2 種構成。角丸 `10px`、高さ 48px（SP は 52px） |
| 信頼要素 | 受賞バッジ、Pマーク／ISMS ロゴ、導入事例、満足度数値 | 実績を持たない MVP では**捏造せず**、算出根拠・データ出典・免責の明示で代替 |
| コンテンツ幅 | 本文ブロックは 1000〜1100px 程度に制限 | `max-width: 1080px` |
| フッター | 多カラムのリンク群、各項目に丸印。最下部に法務リンク | 3 カラム＋法務リンクに簡素化 |

**採らなかった点:** 告知バー、電話番号の常時表示、受賞バッジ、事例カルーセル、複数 CTA の併置。
いずれも MVP の範囲外か、実績のないサービスで真似ると「怪しさ」につながるため（指示書 §24）。

**矛盾の有無:** スクリーンショットと指示書の文章仕様の間に矛盾は見つかりませんでした。
スクリーンショットは B2B SaaS の製品紹介ページで、ワンマケ（BtoC の単機能診断）とは目的が異なるため、
情報量はワンマケ側で大幅に削っています。これは §43「MVP に不要な機能を作らない」に沿った判断です。
